# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Layout

Two independent projects, no root build:

- `backend/` — Spring Boot 3.5 / Java 21 / Maven. Package `com.mockinterviewer`, organised by feature (`company`, `interviewer`, `interview`, `ai`) plus `config` and `common`. Layering: each entity with a repository has one service that alone touches that repository and owns the transactions (`CompanyService`, `InterviewerService` (also photos), `InterviewService` (also the `Interview` aggregate's turns, plan questions and whiteboards)); other services go through it, never another feature's repository (`CompanyRepository.countInterviewers` keeps `CompanyService` from depending on `InterviewerService`, which depends on it). Controllers only translate HTTP (validation, multipart, headers) and call service methods; `AssistantTools` calls the services too.
- `frontend/` — React 19 + TypeScript + Vite. All backend calls go through `src/api.ts`; `src/types.ts` mirrors the backend DTO records by hand, so update both sides together.
  UI is **Mantine 9** (`@mantine/core`, `notifications`, `modals`) with **Tabler icons** (`@tabler/icons-react`); the theme (indigo, component defaults) is `src/theme.ts`; one corner radius everywhere (`md`, the theme default: don't set `radius` per component, and use `var(--mantine-radius-md)` in CSS; only true circles such as avatars and round icons are round), and light/dark follows the system unless changed on the **Preferences** page (`/preferences`, `pages/PreferencesPage`, linked from the gear menu next to Companies; one card per area, add future settings there: appearance, Nikolai's voice, the default hands-free pauses `CHAT_PAUSE` / `INTERVIEW_PAUSE` and the `CODE_SUGGESTIONS` flag from `src/preferences.ts`, all per-browser in localStorage; `INTERVIEW_PAUSE` only preselects the start dialog's per-interview pause). Use Mantine components rather than hand-written CSS; `src/styles.css` only holds what Mantine has no component for (the interview room's stage/tiles/chat bubbles, the code editor layout and highlight.js token colours, and a few helpers), using Mantine CSS variables. Show failures with `notifyError` and ask with `confirmAction` (`src/feedback.tsx`), never `window.alert`/`confirm`. `postcss.config.cjs` sets up `postcss-preset-mantine`.

## Commands

```bash
# Backend (from backend/)
mvn spring-boot:run                                   # http://localhost:8080, won't start without ANTHROPIC_API_KEY (or OPENAI_API_KEY with app.ai.provider: openai)
mvn spring-boot:run -Dspring-boot.run.profiles=local  # application-local.yml: switches to app.ai.provider: openai (env vars, no secrets)
mvn test                                              # all tests (in-memory H2, Claude mocked)
mvn test -Dtest=InterviewFlowTest                     # one class
mvn test -Dtest='InterviewFlowTest#endingBeforeAnyAnswerAbandonsWithoutScoring'  # one method

# Frontend (from frontend/)
npm run dev        # http://localhost:5173, proxies /api → localhost:8080 (vite.config.ts; BACKEND_URL overrides it)
npm run typecheck  # tsc -b; there is no linter or frontend test suite yet
npm run build
```

The default DB is an H2 file at `backend/data/` with `ddl-auto: update` — there are no migrations; delete that directory to reset the schema.

User-facing docs: `README.md` (features, quick start, configuration) and `docs/USER_GUIDE.md` (walkthrough), with screenshots in `docs/screenshots/` taken from a demo instance with fictional data only (never real resumes or interviews). Update them when a feature they describe changes.

## Architecture

**Interview state machine (`interview/InterviewService`).** Code owns the structure, Claude owns the content. `start()` first validates every input and throws `ValidationException` (all field errors at once → `ProblemDetail.errors`), then makes one planning call (`InterviewAi.planInterview`) that writes every main question up front: slot 1 is the candidate's introduction (angle from `InterviewPrompts.INTRODUCTION_ANGLES`; skipped when `includeIntroduction` is false, `Interview.introduction`, null = yes) plus the main questions, asked by the panelist the AI assigned to each slot (see Companies own interviewers; `Interview.interviewers` is an `@OrderColumn` list, lead first). The plan is stored as `InterviewQuestion` rows (`Interview.plan`) before the first is asked. Every `InterviewTurn` links to its planned question (`plannedQuestion`); follow-ups hang off the question being discussed and come from whoever asked it. On each answer Claude scores it and picks `FOLLOW_UP` (it writes the follow-up) or `NEXT_QUESTION`/`END` (the next main question is the plan's, as written); `resolveAction` coerces anything illegal given `max-follow-ups` and whether plan questions remain. Running out of plan, or `/end`, triggers the final evaluation (`COMPLETED`); with no answered turns it is `ABANDONED` with no AI call. `end()` marks the waiting turn `dropped` (kept, but never scored or sent to the AI).

**Round type and question count.** `InterviewService.FormatRequest` (start form, `start_interview` tool): `RoundType` `STANDARD` (default) or `CODING` (a DSA round: every main question is a problem in the code editor; code coerces a missing/SQL language to JAVA and never sets the whiteboard; no fixed follow-up count: the AI decides from the candidate's progress (`turnTask`'s coding guidance says when a problem is done) and `Interview.maxFollowUps` only applies the runaway cap `CODING_FOLLOW_UP_LIMIT` = 12; `InterviewPrompts.CODING_ROUND`, `planTask`/`turnTask`/`finalTask` have coding variants), the number of main questions (introduction excluded: standard 1-`Interview.MAX_QUESTIONS` = 10, default `app.ai.max-questions`; coding 1-`MAX_CODING_PROBLEMS` = 2, default 2; the frontend mirrors these in `StartInterviewModal.QUESTIONS`) and the introduction flag. `Interview.defineFormat` stores them before planning (`plannedQuestions` = main + intro, so `mainQuestions()` works before the plan exists); reattempts copy them. Both are on the summary/detail DTOs (`roundType`, `introduction`).

**Rounds and focus topics.** Optional `Interview.roundName` / `roundDescription` / `focusTopics` (`@ElementCollection`, priority order), copied by reattempts. With focus topics the round is strict: `InterviewService.slotTopics` gives each main question a topic in contiguous blocks (earlier topics take the remainder), `PlanSlot.topic` tells the planner, and `InterviewQuestion.topic` is set to the topic by code (not Claude's label) so `TopicResult` (per-topic averages, follow-ups included, skips 0) adds up. Without topics, the round name/description just steer the plan. The round sits in the setup inside `<round>` tags (treated as data by the system prompt). `topic/TopicCatalog` is the suggestion list plus aliases (`GET /api/topics`); `canonical()` normalises typed topics to catalog names and the frontend `TopicPicker` mirrors it (a tags input whose right-hand button opens the whole catalog by category in a popover). At most `min(8, question count)` topics (`GET /api/topics` returns the cap for the longest round; `TopicPicker`'s `max` lowers it to the chosen count).

**Timing and logs.** `InterviewTurn.responseSeconds` is measured by the browser (`InterviewRoom`: from the question appearing after Join until submit/skip, sent with `/answers` and `/skip`), so it only counts time in the room; null on old rows. `Interview.answeringSeconds()` sums it and `durationSeconds()` is wall clock start→end; both are on the summary and detail DTOs. Question counts are main questions only: `attemptedQuestions` (answered), `skippedQuestions`, and `plannedQuestions` (the plan's size; legacy rows keep the larger count they were set up with). Follow-ups never count. `InterviewService` logs start/answer/skip/complete/abandon with timings and scores (never answer text), and `InterviewAi` logs each Claude call's latency and token usage.

**Skipping.** `POST /api/interviews/{id}/skip` marks the pending turn `skipped` (score 0) and asks the next planned question; no AI call. "Resolved" (`isResolved`) means answered or skipped and drives `pendingTurn`; `hasAnsweredTurns` counts real answers only, so an interview where everything was skipped is abandoned rather than evaluated.

**Reattempts and question status.** `POST /api/interviews/{id}/reattempt` creates a new `Interview` with `retakeOf` = the original (always the original, never another reattempt), `attempt` = max + 1 (null on old rows means 1) and a copy of the original's plan, so the main questions are identical; follow-ups are generated fresh from the new answers through the normal `answer()` path. Any ended (completed or abandoned) interview with a plan can be reattempted (`canBeReattempted`, exposed as `reattemptable`). `InterviewDetail.questions` (`QuestionResult`) lists every planned question with its status (`ANSWERED`, `SKIPPED`, `CURRENT`, `NOT_ATTEMPTED`), main answer/score and follow-ups; the report compares scores with the previous completed attempt by plan `position`. `LegacyPlanBackfill` calls `InterviewService.backfillLegacyPlans()` at startup to give pre-planning interviews a plan rebuilt from their asked main questions. Deletion is per interview only: `DELETE /api/interviews/{id}` removes the original and all reattempts even when given a reattempt id. `originalOf` unproxies `retakeOf` and `initialised()` loads the associations DTOs read; lazy proxies used after the transaction caused `LazyInitializationException`s here.

**Ask AI (study guides).** On an ended interview, the report's `components/AskAi` button (next to the score of each main question and each answered/skipped follow-up) opens a large Mantine `Modal`: the candidate's answer (left) beside a first-person "better answer" (right, the model answer), then a prioritised reading list, based on what the candidate said (or what a good answer covers, if skipped/not reached). `POST /api/interviews/{id}/questions/{questionId}/study-guide` (main questions, any status) and `POST /api/interviews/{id}/turns/{turnId}/study-guide` (follow-ups only) call `InterviewAi.studyGuide` / `followUpStudyGuide` (`InterviewPrompts.studyGuideTask` / `followUpStudyGuideTask`). Each is generated once and stored as an embedded `StudyGuideNotes` (`modelAnswer`, `studyTopics` as `topic\treason` lines): main questions on `InterviewQuestion` (per attempt, since each attempt has its own plan rows), follow-ups on `InterviewTurn`. `QuestionResult.studyGuide` and `TurnResponse.studyGuide` carry them.

**Whiteboard (Excalidraw).** The room's **Whiteboard** button swaps the stage for an Excalidraw board (`components/Whiteboard`, lazy-loaded; the interviewers shrink to a centred `filmstrip`). The app header is collapsed for the whole time in the room (`src/chrome.ts` `setHeaderHidden`, read by `App`'s `AppShell`); the room's own header (`.room-header`, on the body's columns) has the title and current question with **Skip Question** at the right of the people's column, and the timers (`components/Clock`, `Clocks`, shown after Join) as wide as the chat column below. While the board is open the room maximises it: the room breaks out of the centred container to the full window width (`.room.board-mode`) and the chat narrows to 340px. Data logic lives in `src/whiteboard.ts` without importing the editor: one board per main question, carried through its follow-ups, drafted to localStorage (`whiteboard:<interviewId>:<mainTurnId>`, with the last submitted version, cleared when the interview ends), else reopened from the last submitted scene (`GET .../turns/{turnId}/whiteboard/scene`). On submit, a board that changed since it was last sent goes with the answer (`AnswerRequest.whiteboard`: base64 PNG on white, at most 1568 px, plus scene JSON and a text `outline()` of labelled shapes and arrow connections); a drawing alone is a valid answer (stored as `WHITEBOARD_ONLY_ANSWER`). The **Components** palette (`components/ComponentPanel`) is our own Excalidraw `Sidebar` (`PALETTE`), the only one shown: Excalidraw's default sidebar (Search and Library tabs) is never opened and its top-right Library button is hidden by CSS; Excalidraw's main menu (hamburger) is hidden too; a **Components** button top left opens the palette whenever it is closed, and a **Clear** button right after Undo/Redo (portalled into Excalidraw's bottom-left bar, so it moves with it) empties the board after `confirmAction`, as one undoable step, and it opens docked by itself on an empty board. It has Core / AWS / Azure tabs, each grouped by category with search; click places in the middle of the visible board, drag drops as `application/vnd.excalidrawlib+json`. **Core** (`components/whiteboardLibrary.ts`, `coreComponents()`): basic shapes (box, circle, decision, note, dashed boundary) plus generic system design components (clients, edge & networking, compute incl. stacked Service Group / Worker Group, messaging, data with cylinders, security & operations), each one labelled, arrow-bindable shape with `customData.component` (survives renaming; `outline()` reports `"Orders" (Relational DB)`); drawing-only parts carry `customData.decoration` so the outline skips them. **AWS / Azure** are the official architecture icon packages (AWS Icon package 07/31/2026, Azure Public Service Icons V24), one SVG each under `frontend/public/whiteboard-icons/` (README there), listed with their categories in `public/whiteboard-icons/index.json` (fetched at runtime by `ComponentPanel`; missing means the AWS/Azure tabs show how to import them); both are generated by `frontend/scripts/import-cloud-icons.py` from the unzipped packages (rerun it to update) and are git-ignored (licensed for diagrams, not redistribution), so a fresh clone has none. An icon is placed as a group: the SVG as an image (`decoration`), an invisible zero-opacity filled rectangle over it carrying `customData.component` (e.g. `AWS Lambda`, `Azure Cosmos DB`; Excalidraw won't bind arrows to images, and only binds from inside filled shapes), and a label text (`customData.iconLabel`), so the outline names icons and their connections. The sidebar docks on the left and the shape settings panel sits on the right (swapped from Excalidraw's default by CSS in `styles.css`); `swapUiOffsets` in `Whiteboard.tsx` finds the mounted editor through the React fiber, replaces its `getEditorUIOffsets` so zoom-to-fit still avoids the panels, and picks the mounted editor's API (StrictMode constructs a throwaway editor that also calls `excalidrawAPI`). Hands-free auto-send (`useSilenceSubmit`) is off entirely while the board is open (the mic still dictates; the candidate presses Submit), and the silence clock starts fresh when it closes. The backend keeps it in `TurnWhiteboard` (own table, `@OneToOne` lazy from `InterviewTurn`, PNG checked by magic bytes) and serves `.../whiteboard.png` (`whiteboardUrl` on turns and `QuestionResult`; the report and chat show it). Claude asks for drawings: `PlannedQuestion.whiteboard` → `InterviewQuestion.whiteboard` (copied by reattempts, never slot 1) and `TurnDecision.whiteboard` for follow-ups → `InterviewTurn.whiteboardRequested`, which opens the board in the room. `InterviewPrompts.transcriptParts` puts each question's latest board image (with its `<whiteboard_outline>`, treated as data) into the transcript; earlier boards of the same question are only mentioned. The header's **Whiteboard** button opens `/whiteboard` (`pages/WhiteboardPage`): the same `Whiteboard` component and library, full window (routed outside the `AppShell`, so no header or Nikolai; a floating × close button sits in Excalidraw's top-right via `topRight` and goes back, or home if opened directly), not tied to any interview, saved per browser under `whiteboard:scratch` (`loadScratch`/`saveScratch`).

**Code editor (CodeMirror 6).** The room's **Code** button swaps the stage for `components/CodeEditor` (lazy-loaded `@uiw/react-codemirror` with `@codemirror/lang-java`, `lang-python`, `lang-sql`), the same way as the whiteboard: `InterviewRoom` has one `workspace` state (`'none' | 'board' | 'code'`, one at a time, `.room.workspace-mode` maximises either) and hands-free auto-send is off while either is open. Languages are `CodeLanguage` (`JAVA`, `PYTHON`, `SQL`, mirrored in `types.ts` and `codepad.ts`); the toolbar picks the language and, for SQL, a dialect (`code:sql-dialect`, only changes keyword suggestions). Suggestions follow the `CODE_SUGGESTIONS` flag (`src/preferences.ts`, default on; toolbar switch and Preferences card): off leaves the autocompletion extension out entirely. Python's package completes built-ins and names in scope, SQL's keywords per dialect; `components/codeCompletions.ts` adds Java keywords, common types, words in the file and snippets for Java and Python. Keep `extensions`, `basicSetup` and `onChange` stable (memoised/ref'd): `@uiw/react-codemirror` reconfigures the editor whenever they change, which closes the suggestion list. Data logic lives in `src/codepad.ts` without importing the editor: one `CodeBuffer` (`language`, `source`, `submittedSource`) per main question, carried through its follow-ups, drafted to localStorage (`code:<interviewId>:<mainTurnId>`, cleared when the interview ends), else rebuilt from the last submitted code (`turns[].code`), else a starter in the requested language or the last one used (`code:language`): the main question as a wrapped line comment (`questionComment`/`starterSource`), with `submittedSource` set to it so it doesn't count as a change (`submittedSource` is really the "unchanged" baseline). A follow-up with `codeRequested` prepends its own comment block once (baseline moved with it when the code was unchanged), and switching language rewrites whole-line comments to the new syntax (`convertComments`); an untouched buffer with no draft switches to the requested language. The editor opens with the cursor at the end, below the comments. On submit (or Ctrl/Cmd+Enter in the editor) changed code goes with the answer (`AnswerRequest.code`: `language` + `source`, at most `TurnCode.MAX_SOURCE_CHARS` = 50k); code alone is a valid answer (`CODE_ONLY_ANSWER`, or `BOARD_AND_CODE_ANSWER` with a drawing). The backend keeps it as an embedded `TurnCode` on `InterviewTurn` (small text, no own table) and returns it as `code` on `TurnResponse` and `QuestionResult`; the chat, report and Ask AI show it read-only with `components/CodeBlock` (`@mantine/code-highlight` + highlight.js core with only java/python/sql; token colours in `styles.css`), and `splitFences` renders fenced code in Ask AI's model answers. Claude asks for code: `PlannedQuestion.code` / `TurnDecision.code` (`AiOutputs.CodeEditor`: `NONE` or a language) → `InterviewQuestion.codeLanguage` (copied by reattempts, never slot 1) and `InterviewTurn.codeRequested`, which opens the editor in that language (unless code is already written); when both whiteboard and code are asked for, the whiteboard wins. `InterviewPrompts.transcriptParts` puts each question's latest code in `<candidate_code language="…">` (treated as data); earlier versions are only mentioned. The code is never run.

**AI calls run inside the DB transaction on purpose**: if Claude fails, the answer/interview isn't persisted and the client can retry the same request. Keep that property when refactoring.

**AI providers (`ai/`).** All AI calls go through `ai/AiProvider`, selected by `app.ai.provider` (`anthropic` | `openai`, the `AiProperties.Provider` enum; unknown values fail binding). Each provider has its own block bound natively by Spring to a record of the sealed `config/AiProviderSettings`: `app.ai.anthropic.*` → `Anthropic` (`api-key`, `base-url`, `model`, `turn-effort`, `final-effort`) and `app.ai.openai.*` → `OpenAi` (the same plus `organization`); each fills its own default model, blank means unset, and `AiProperties.selected()` returns the chosen block. Each record is self-contained: `createProvider()` validates its own settings, fails startup with its own `IllegalStateException` message when the key is missing (neither `api-key` nor its SDK's env var), and builds its client and provider; `config/AiProviderConfig` just calls `selected().createProvider()`. Only the selected block is validated. Tests get a dummy key from `src/test/resources/config/application.properties`. `AiProvider` has `structured()` (one stateless request with neutral `Content` parts: `Text` (with a cache-breakpoint flag), `Document`, `Image`, answered as an `AiOutputs` record) and `newChat()` (a tool-using `Chat` that keeps history in the vendor's own format, with `checkpoint()`/`rollback()`). `ai/anthropic/AnthropicProvider` is the Messages API (structured outputs, `cacheControl` at the breakpoint, refusal fallback beta); `ai/openai/OpenAiProvider` is Chat Completions (strict structured outputs from the same records, PDF as a base64 file part, images as data URLs, efforts sent as `reasoning_effort` (blank for non-reasoning models), `base-url` for OpenAI-compatible servers). `ApiExceptionHandler` maps both SDKs' auth/rate-limit/other errors. Effort is `AiProvider.Effort.TURN` (per answer, Nikolai) or `FINAL` (plan, evaluation, study guides). Prompts are written for Claude and shared by both providers.

**Interview AI calls.** `InterviewAi` makes stateless single-message calls — the transcript is rebuilt from `InterviewTurn` rows every time (`InterviewPrompts.transcript`), so there's no API-side conversation state. Content order is resume document → interview setup (prompt-cache breakpoint) → transcript + task; keep stable content before the breakpoint. Responses use structured outputs derived from the records in `AiOutputs` (`@JsonPropertyDescription` text is part of the prompt). Anthropic requests opt into server-side refusal fallback (`fallbacks: "default"` + `server-side-fallback-2026-07-01` beta header). Model and effort come from the selected provider's block (`AiProperties.selected()`). Candidate answers are wrapped in `<candidate_answer>` tags and the optional job description (stored on `Interview`) sits in the setup inside `<job_description>` tags; the system prompt treats both as data.

**Companies own interviewers.** Each `Interviewer` has a required `company` (`@ManyToOne`; the column is nullable only so `ddl-auto: update` could add it). Interviewers are chosen from that company only, by the AI from the full context: before planning, `InterviewAi.assignPanel` (`InterviewPrompts.panelTask`, `AiOutputs.PanelAssignment`) sees the resume, role, job description, round, slot topics and the company's whole roster (ids, titles, expertise, background) and picks the panel (lead first, who asks the introduction) and who asks each slot. `InterviewerAssigner.resolve` keeps it legal, as `resolveAction` does for turns: one-on-one needs 1, a panel `min(app.ai.panel-size (minimum 2), roster)`; unknown/repeated ids are dropped, a short panel is filled at random, a slot whose asker isn't on the panel falls back to rotation, every panelist gets at least one main question, and a null choice means a random panel in rotation. No AI call when the company has a single interviewer. Reattempts copy the panel and plan, so they never re-choose. The UI has no separate interviewers page: `/companies` is a logo grid (`Company.logoUrl`, with a monogram fallback) and `/companies/:id` shows the company details and manages its interviewers (`GET /api/interviewers?companyId=`). `CompanyResponse.interviewerCount` drives the grid and the start-interview company picker.

**Persistence.** "Past interviews" = `Interview` rows with status `COMPLETED`/`ABANDONED` plus their `InterviewTurn` rows (question, answer, follow-up flag, 0–10 score, feedback); overall score is 0–100. Resumes (PDF or plain text) are stored as bytes on `Interview` and sent to Claude as a document block on every call. Entities are never serialised directly — controllers map them to the `*Dtos` records; `open-in-view` is off, so touch lazy associations inside a transaction.

**Voice and video (frontend).** `src/speech.ts` wraps the Azure Speech browser SDK: TTS via SSML (`SPEAKING_RATE` prosody, currently 0% = normal pace) to a `SpeakerAudioDestination` (resolve on `onAudioEnd`) and continuous STT dictation. It fetches tokens from the backend's `speech/SpeechTokenService` (`/api/speech/token`; the Azure key stays server-side; tokens live 10 min and the backend reuses one for 9, so it returns `expiresInSeconds` and the browser caches only until a minute before that; a websocket refusal ("Unable to contact server" / 1006 / 401) is retried once with a fresh token in `speak()` and `listen()`); `enabled: false` means the UI runs text-only. `speak()` uses a generation counter so a superseded or StrictMode-double-invoked call never plays over a newer one; keep that when changing it. `pages/InterviewRoom.tsx` is the video-call room: a lobby modal (the Join click is the user gesture that unlocks audio), the `people-stage` (one-on-one and panel alike, no floating camera: interviewers then the candidate last, in equal tiles at most 2 per row, each row half the stage height and centred, `--cols`/`--rows` from `gridShape`; clicking any tile spotlights that person as the `hero` tile with the others in a small centred `spotlight-strip` on top, clicking the hero goes back; only the hero shows an interviewer's title, other tiles and filmstrips show names only), and the chat sidebar. Each new pending question is spoken once (`spokenRef`), and hands-free mode then opens the mic and, via `useSilenceSubmit`, submits the answer after `Interview.answerPauseSeconds` without speech (chosen in the start dialog, 3-60 s, default 10 when null, copied by reattempts, also a `start_interview` tool argument; nothing said, nothing sent; `SilenceCountdown` shows the last 5 s, or half for short pauses; any recognised speech calls `heard()` and resets it). Nikolai's chat uses the same hook whenever his mic is on, with the `CHAT_PAUSE` preference (default 5 s, countdown for the last 3 s), a **Hands-free** toggle in the chat header (default on) replaces a mute button: on, he speaks replies, the mic opens when he finishes uninterrupted (and immediately when the chat is reopened after the first greeting), and silence sends; off, he is silent, nothing auto-listens or auto-sends, and the mic is click-to-dictate (`say()` + a `speechTurn` counter that closing, toggling hands-free, typing, sending and New chat bump; an auto-opened mic with nothing said switches off after 30 s), and while dictating Enter stops the mic and sends immediately (a window listener, skipped when focus is in another field on the page). Voices (`src/voices.ts`) and avatars (`src/avatar.ts`, DiceBear seeded by name) fall back to defaults when `Interviewer.voice` / `photoUrl` are null; the default voice is picked (stably, by id) among voices of the gender `genderFromName` infers from the first name (name lists, then endings), so set a voice explicitly when the guess is wrong. Interviewer photos are uploaded files (`interviewer/PhotoStorage`, under `app.uploads.dir`, default `backend/data/uploads/interviewers/`): the DB holds only `Interviewer.photoFile`, the image type is detected from magic bytes, and each upload gets a new file name so `getPhotoUrl()` (`/api/interviewers/{id}/photo?v=<file>`) can be cached. The seeded photos are AI-generated faces, not real people. The camera (`components/useCamera.ts`) is a local preview only.

**Assistant tools, MCP server and Nikolai (`assistant/`).** `AssistantTools` defines the app's actions once (`list_companies`, `add_company`, `list_interviewers`, `add_interviewer`, `list_interviews`, `list_resumes`, `get_resume`, `start_interview`) and runs them through the same services as the REST API (request records are Bean-validated by hand); failures come back as error results, not exceptions. Companies resolve by id or (partial) name. `list_resumes` groups the resumes past interviews used by file content (SHA-256), most recently used first; `get_resume` returns one interview's resume (default: the latest) as text, PDFs via PDFBox (`ResumeText`), capped at 100k characters. `start_interview` takes the resume from `resumeText`, else a resume attached in Nikolai's chat, else the most recent interview's (`InterviewService.latestProfile`, which also supplies the default candidate name). They are served two ways: `McpServerConfig` registers the MCP Java SDK's stateless Streamable-HTTP servlet at `/mcp` (no auth; only loopback Host/Origin accepted; `claude mcp add --transport http interview-me http://localhost:8080/mcp`), and `NikolaiService` gives them to the configured provider's `AiProvider.Chat` in a manual tool loop for the in-app assistant (`POST /api/nikolai/chat`, multipart: `conversationId`, `message`, optional `resume`). Nikolai is a Russian career-coach persona (`NikolaiService.SYSTEM`; replies are spoken, so no markdown; he doesn't list his abilities unless asked); the chat's opening line is a random client-side greeting (`nikolaiGreeting()` in `nikolai.ts`, name + a question, never the same twice running), so the prompt tells him not to introduce himself again; conversations are in memory (6 h TTL, max 100) and append-only, each response stored via the SDK's `toParam()` (Claude's thinking blocks replay unchanged), and a failed turn is rolled back (`Chat.rollback`). The frontend `components/NikolaiWidget` is the floating bottom-right button (just his face, `nikolaiAvatar` in `src/avatar.ts`: a fixed DiceBear persona with a walrus moustache and big smile to fit his character, not the name-seeded look) and chat panel (type, or dictate with the mic, which sends when stopped; attach a resume; replies are spoken in a Russian Azure voice reading English for a Russian accent (picked from `NIKOLAI_VOICES` in `nikolai.ts` on the Preferences page, `useNikolaiVoice`/`setNikolaiVoice`, remembered in localStorage; default `ru-RU-Lev:MAI-Voice-2.1-Flash`)). After write tools it fires `DATA_CHANGED` so every `useAsync` reloads, and `start_interview` navigates to the new room. `InterviewRoom` hides him (`hideNikolai`) because it has its own mic and voice.

**Errors.** `common/ApiExceptionHandler` returns `ProblemDetail`; the frontend shows its `detail` field. Anthropic/OpenAI SDK auth/rate-limit/other failures map to 502/503; unusable model output throws `AiResponseException`; `ValidationException` adds an `errors` map that the start form (`components/StartInterviewModal`, opened over the dashboard by the `/interviews/new` route) shows per field (`ApiError.errors`).
